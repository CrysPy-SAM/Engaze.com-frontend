# 13. Top 10 Engineering Challenges & Problem Solving — Engaze

This document covers the **10 most critical real-world engineering challenges** solved during the design, development, and production hardening of Engaze. Each case study follows the **Problem $\rightarrow$ Investigation $\rightarrow$ Root Cause $\rightarrow$ Solution $\rightarrow$ Alternative Analysis** framework favored in Senior Engineering interviews.

---

## Challenge 1: Google Play Protect "Harmful App Blocked" on Android APK

### 1. The Problem
Upon building and distributing the native Android APK (`com.engaze.date`), Android devices blocked installation with a high-severity Google Play Protect alert: *"Harmful app blocked: This app can put your device or data at risk."*

### 2. Investigation
* Audited the final merged `AndroidManifest.xml` generated by Gradle.
* Traced all native Java methods in `MainActivity.java` and third-party dependencies.
* Inspected APK certificate signing fingerprints and checked Google Play Protect heuristic detection documentation.

### 3. Root Cause
1. **Dangerous Installer Permission:** `AndroidManifest.xml` requested `android.permission.REQUEST_INSTALL_PACKAGES`. Modern Android versions flag any non-app-store application requesting package installation privileges as a potential trojan/dropper.
2. **Native Self-Installing Code:** `MainActivity.java` contained custom code that opened an `HttpURLConnection` stream, downloaded raw `.apk` bytes to disk, and invoked an `ACTION_VIEW` intent with a `FileProvider` URI pointing to package installer components.

### 4. Solution Implemented
* Removed `REQUEST_INSTALL_PACKAGES` from `AndroidManifest.xml`.
* Replaced the native self-install code with a **Browser-Delegated Update Flow** in `AppUpdateChecker.jsx`. When an update is detected, the app invokes an `ACTION_VIEW` intent with the GitHub Releases download URL, delegating the download and install flow to the user's verified system browser (Chrome/Firefox).

### 5. Why Chosen & Alternatives Considered
* **Alternative considered:** Publishing to the Google Play Store immediately. (Rejected as a temporary fix because private beta testing required direct APK sideloading).
* **Chosen Solution:** Cleanly separates application logic from package installation, satisfying Google Play Protect security heuristics.

## Challenge 2: Android Photo Upload Failure on AWS S3 (Content-Type & CORS Mismatch)

### 1. The Problem
Profile photo uploads functioned properly on desktop and mobile web browsers, but failed 100% of the time when running inside the Android Capacitor app, returning `403 Forbidden` errors.

### 2. Investigation
* Inspected Chrome DevTools remote debugging logs connected to the running Android WebView.
* Observed two distinct failures:
  1. Preflight `OPTIONS` requests failed with `CORS policy: No 'Access-Control-Allow-Origin' header`.
  2. Binary `PUT` requests returned AWS `403 SignatureDoesNotMatch`.

### 3. Root Cause
1. **WebView Origin Discrepancy:** In `capacitor.config.json`, `"androidScheme": "https"` forces the Android WebView to serve the app from `https://localhost`. The AWS S3 bucket's CORS policy only permitted `https://www.engaze.date`.
2. **MIME Type Drift:** Android photo gallery pickers often return `file.type` as `""` (empty) or `"image/jpg"`. In Step 1, the frontend requested a presigned URL defaulting to `"image/jpeg"`. In Step 2, the old Axios uploader defaulted to `"application/octet-stream"`. AWS SigV4 cryptographic signatures include the exact `Content-Type` header; a mismatch between Step 1 and Step 2 invalidates the signature, causing S3 to reject the upload.

### 4. Solution Implemented
1. Engineered `normalizePhotoContentType(file)` in `photoUpload.js`, enforcing canonical MIME normalization (`image/jpg` $\rightarrow$ `image/jpeg`, extension fallback).
2. Bound the exact same normalized MIME type to both presigned URL generation and the binary Axios PUT header.
3. Updated the AWS S3 CORS configuration to include `"https://localhost"` and `"capacitor://localhost"`.

## Challenge 3: Concurrent Mutual Match Race Conditions (Duplicate Matches)

### 1. The Problem
If Alice and Bob swiped "Like" on each other at the exact same second, two concurrent HTTP requests hit `/api/v1/discovery/swipe`. Both detected a mutual like, resulting in **two distinct duplicate Match records** and **two separate Conversation records** in MongoDB.

### 2. Investigation
* Traced the swipe controller execution under concurrent simulated loads.
* Found that the check-then-insert pattern (`if (!matchExists) { await Match.create(...) }`) suffered from classic time-of-check to time-of-use (TOCTOU) race conditions.

### 3. Root Cause
Without database-level unique constraints, concurrent Node.js async operations both evaluated the check to `false` before either completed insertion.

### 4. Solution Implemented
1. Created a static helper method on the `Match` schema to generate a **Deterministic Canonical Pair String**:
   ```javascript
   matchSchema.statics.getCanonicalPair = function(idA, idB) {
       return idA < idB ? `${idA}_${idB}` : `${idB}_${idA}`;
   };
   ```
2. Added a unique index on `userPair`:
   ```javascript
   matchSchema.index({ userPair: 1 }, { unique: true });
   ```
3. Wrapped match creation in a `try/catch` block catching MongoDB duplicate key error code `11000`. If duplicate key is caught, the second request safely ignores the error and returns the existing match.

## Challenge 4: Render Free-Tier Sleeping Instance Network Timeouts

### 1. The Problem
On Render's free tier, backend containers enter a sleep state after 15 minutes of inactivity. When a user opened the app, the container took 30–50 seconds to spin up. Standard Axios API requests timed out after 10 seconds, causing immediate red network error banners across the screen.

### 2. Investigation
* Inspected network waterfall charts on cold boots.
* Verified that the backend successfully started after 35 seconds, but the frontend had already given up and unmounted components.

### 3. Solution Implemented
1. Configured the global Axios client in `AuthContext.jsx` with an extended **60-second timeout**:
   ```javascript
   const api = axios.create({
       baseURL: `${server}/api/v1`,
       timeout: 60000, // Accommodates cloud container cold boot
   });
   ```
2. Added an intelligent retry mechanism and created `RouteErrorBoundary` so users receive a calm "Waking up server..." status rather than a crash.

## Challenge 5: WebSocket State Fragmentation Across Clustered Nodes

### 1. The Problem
When scaling the Node.js backend across multiple process instances or container replicas, real-time messages and WebRTC call signals failed intermittently whenever Alice and Bob were connected to different server instances.

### 2. Root Cause
Standard Socket.IO instances store socket connections in local process memory. An event emitted via `io.to("user:Bob")` on Server A cannot reach Bob's socket on Server B.

### 3. Solution Implemented
Integrated **`@socket.io/redis-adapter`**:
* When an event is emitted to a room, the Redis adapter publishes the event to a shared Redis Pub/Sub channel.
* All peer server instances receive the message and broadcast it to any locally connected client sockets matching that room.
* Architected a **graceful fallback**: if Redis is not configured (such as during local development), the server automatically operates in local memory mode without crashing.

## Challenge 6: WebRTC Hardware Camera Lock & Memory Leaks

### 1. The Problem
After ending a video call, the browser tab still showed the green camera recording indicator, and the Android status bar indicated active microphone recording. Attempting to start a subsequent call failed with `NotReadableError: Device in use`.

### 2. Root Cause
Calling `pc.close()` closes the WebRTC peer connection but does **not** stop the underlying hardware tracks on the `MediaStream` returned by `getUserMedia()`.

### 3. Solution Implemented
Engineered an explicit media track lifecycle manager in `DirectCallContext.jsx`:
```javascript
const stopLocalMedia = () => {
    if (localStreamRef.current) {
        localStreamRef.current.getTracks().forEach((track) => {
            track.stop(); // Explicitly releases OS hardware lock
        });
        localStreamRef.current = null;
        setLocalStream(null);
    }
};
```
Bound this teardown to call completion, call decline, socket disconnects, and React component unmount handlers.

## Challenge 7: Insecure Production Startup Configurations

### 1. The Problem
Junior developers or automated CI deployment scripts could accidentally spin up production containers without setting a cryptographically secure `JWT_SECRET`, exposing user sessions to forgery.

### 2. Solution Implemented
Engineered a strict startup validator in `backend/src/config/jwt.js`:
* Executes synchronously before database connections or HTTP port binding.
* In production, asserts that `JWT_SECRET` is defined, $\ge 32$ characters long, and does not match a list of insecure placeholders (`"secret"`, `"changeme"`).
* If any condition fails, the process logs a fatal error and invokes `process.exit(1)`, failing closed.

## Challenge 8: Google OAuth Failure Inside Android Capacitor WebView

### 1. The Problem
Tapping "Sign in with Google" inside the Android mobile app resulted in `403 disallowed_useragent` from Google's authorization servers.

### 2. Root Cause
Google deliberately blocks OAuth requests initiated inside embedded WebViews to protect against credential interception attacks.

### 3. Solution Implemented
Overrode `BridgeWebChromeClient.onCreateWindow()` in `MainActivity.java`:
* Detects when Google's SDK attempts to open a popup window.
* Spawns an isolated modal Dialog WebView with custom settings (`JavaScriptEnabled`, `SupportMultipleWindows`).
* Intercepts the final redirect back to `https://localhost` or the production callback URL, retrieves the auth token, and closes the popup dialog automatically.

## Challenge 9: Unread Message Badge Desynchronization Across Active Tabs

### 1. The Problem
When a user had Engaze open in two browser tabs or on both phone and web, reading a message in Tab A did not clear the unread counter badge in Tab B.

### 2. Solution Implemented
* Switched unread badge tracking from local client calculations to an **authoritative server-driven event model**.
* When messages are marked as read in Tab A (`chat:read`), the server updates MongoDB and broadcasts `chat:unread-count` directly to `user:<userId>`:
  ```javascript
  io.to(`user:${userId}`).emit("chat:unread-count", { unreadCount, conversationsUnread });
  ```
* All active tabs and devices receive the authoritative count simultaneously and synchronize their badges.

## Challenge 10: Server Memory Exhaustion from Multipart File Uploads

### 1. The Problem
Early photo upload implementations funneled multipart files through Express memory buffers. Concurrent 5MB image uploads from multiple users caused Node.js process memory spikes and event loop blocking.

### 2. Solution Implemented
Transitioned to **Client-Direct Presigned S3 Uploads**:
* The server only generates an authorized AWS SigV4 URL containing a 15-minute expiration timestamp and cryptographic HMAC signature.
* The client streams the binary payload directly to AWS S3.
* Server memory usage dropped to virtually zero bytes per upload.
